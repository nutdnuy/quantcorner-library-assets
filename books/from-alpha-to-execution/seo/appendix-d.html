Checklist สำหรับวิจัยและ Production

ภาคผนวกนี้เปลี่ยน checklist เดิมจากรายการ “ควรมี” ให้เป็น decision gates ที่ใช้ได้ตั้งแต่ research
review, paper/shadow trading, pilot capital จนถึง production change management หลัก
สำคัญ คือ หลัก ฐานบางชนิด สามารถให้ คะแนนได้ แต่ ความปลอดภัย บางข้อ เป็น hard gate และห้ามนำ
คะแนนด้านอื่นมาชดเชย
  แนวคิดสำคัญ
  Signature ของ ผู้ เขียน: A2E–GATES. ก่อน deploy ระบบ ต้อง ตอบ ห้า ชั้น Grounded
  hypothesis, Auditable data/ ตัว แบบ, Tradeable net edge, Execution safety และ
  Surveillance/stop capability การผ่าน GATES หมายถึง “พร้อมให้พิจารณาใช้ทุน” ไม่ได้หมาย-
  ความว่ากลยุทธ์จะทำกำไรแน่นอน


D.1 Research Checklist
D.1.1 R1: Problem, Hypothesis และ Economic Rationale
1. คำถามวิจัยและ decision horizon ถูกนิยามก่อนค้นหาตัวแบบ
2. Hypothesis falsifiable และระบุสิ่งที่จะถือว่า “ไม่สนับสนุน” สมมติฐาน
3. Economic/behavioral/microstructure rationale ชัดเจนและแยกจากคำอธิบายย้อนหลัง
4. Benchmark/baseline ถูกกำหนดก่อนเปรียบเทียบตัวแบบซับซ้อน
5. Universe และ eligible instruments ถูกนิยามแบบ point-in-time

D.1.2 R2: Data Integrity และ Point-in-Time Audit
1. มี data dictionary: field, unit, timezone, frequency, source และ availability time
2. Raw data snapshot เก็บแบบ immutable/replayable ตามข้อจำกัดสิทธิข้อมูล
3. Corporate actions, symbol mapping และ universe membership ถูกจัดการตามเวลา

D.1.3 R3: Statistical Design
1. Train/validation/test เป็น chronological split ที่สอดคล้องกับ horizon
2. Label overlap ถูก purge/embargo เมื่อจำเป็นตาม research design

4. Dependence/heteroskedasticity ถูกคำนึงในการอนุมาน
5. รายงาน effect size และ economic significance ไม่ใช่เฉพาะ p-value
6. จำนวนการทดลอง parameter search และ alpha variants ถูกบันทึก
7. มี multiple-testing/data-snooping control ที่เหมาะสมเมื่อมีการค้นหาหลายแบบ
8. มี robustness ต่อ regime, subperiod, universe และ reasonable parameter perturbation

D.1.4 R4: Portfolio, Cost และ Execution Realism
1. Signal timing สอดคล้องกับเวลาที่ข้อมูลทราบและเวลาที่สั่งซื้อขายได้จริง
2. Mapping จาก alpha score ไป position ถูกระบุเป็นสมการ/algorithm
3. Transaction fees, spread, slippage และ market impact มีหน่วยและสมมติฐานชัดเจน
4. ตัวแบบการจับคู่คำสั่ง/queue assumption เหมาะกับ data resolution และ order type
5. Turnover, capacity, ADV/depth participation และ concentration ถูก stress test
6. Risk constraints สอดคล้องกับ leverage, factor, liquidity และ loss budget
7. รายงาน gross edge และ net edge แยกกัน

D.1.5 R5: Reproducibility และ Research Governance
1. code/data/config/รุ่นของตัวแบบ ทำซ้ำผลหลักได้
2. random seed และ stochastic simulation policy ถูกบันทึก
3. Research notebook ไม่เป็นแหล่ง production logic เพียงแห่งเดียว

D.2 Production Checklist
D.2.1 P1: Market Data Health
1. feed connection และ entitlement ถูกต้องตาม environment
2. sequence, duplicate, gap และ correction monitoring เปิดใช้งาน
3. timestamp resolution, clock health และ staleness thresholds ถูกกำหนด
4. reference data เช่น tick/lot/session/status พร้อมและ versioned
5. stale/degraded feed มี policy ว่าหยุด ลด risk หรือ switch source อย่างไร

D.2.2 P2: Pre-trade Risk Controls

D.2.4 P4: Kill Switch และ Safe State
1. kill switch ถูกทดสอบใน environment ที่ใกล้ production
2. operator ทราบว่า kill แบบใด block new orders, cancel orders หรือ flatten risk
3. kill action มี authentication/authorization และ audit trail
4. failure ของ monitoring ไม่ทำให้ risk gate ถูก bypass
5. restart/recovery ไม่สร้าง duplicate order หรือ state divergence

D.2.5 P5: Observability
1. latency p50/p95/p99 แยกตาม stage และ strategy
2. market-data staleness/gaps/duplicates มี dashboard/alert
3. order reject/cancel/fill ratios ถูกติดตาม
4. P&L, slippage, spread capture, adverse selection และ implementation shortfall มี

D.3 Deployment Ladder และ Gate Evidence
การ deploy ไม่ควรกระโดดจาก backtest ไป full production ลำดับที่แนะนำคือ
                       Research → Replay → Paper
                                  → Shadow → Pilot → Production

แต่ละขั้นต้องมี exit criteria ของตนเอง

D.3.1 Research → Replay
ต้องผ่าน PIT audit, deterministic pipeline, baseline/OOS และตัวแบบต้นทุน ขั้นต้น

D.3.2 Replay → Paper
ต้องผ่าน event/order-state replay, fault cases และ reproducibility manifest

D.3.3 Paper → Shadow
ต้องมี market-data/live-state parity, latency monitoring และ no-order decision comparison

D.3.4 Shadow → Pilot
ต้องพิสูจน์ decision consistency, risk gates, kill switch และ operational ownership

D.3.5 Pilot → Production
ต้องผ่าน realized cost/fill/slippage comparison กับ assumptions และไม่มี unresolved severity-
high control failure

3. ลด/หยุด risk ตาม runbook และบันทึก operator action

D.6 การทบทวนตัวแบบ และ Periodic Re-approval
ตัวแบบสำหรับ production ควรมี review cadence ตาม materiality และ horizon แต่ trigger-based
review สำคัญกว่า calendar เพียงอย่างเดียว trigger ตัวอย่างคือ
1. feature/data definition เปลี่ยน
2. venue/rule/tick/lot/session semantics เปลี่ยน
3. realized slippage/fill แตกต่างจากตัวแบบ อย่างมีนัยสำคัญเชิงเศรษฐศาสตร์
4. predictive calibration/IC/net edge เสื่อมต่อเนื่อง
5. risk limit breach หรือ incident สำคัญ
6. dependency/ตัวแบบ/library upgrade เปลี่ยน numerical behavior
